XAML compiler service: API changes (XamlCompilerService.ApiVersion)

v1 (1089897cb)
  XamlCompilerService(CompilerInputs buildInputs, string outputPath = null)
  AllXamlFiles, CompilePass1(files), CompilePass2(files, byte[] localAssemblyImage, bool regenerateTypeInfo, string localAssemblyPath)
  XamlCompileResult: Success, Elapsed, GeneratedText, GeneratedXbf, XamlTypeInfoMayBeStale, Diagnostics, Markers

v2 (hot reload code generation)
  + XamlCompilerService.ApiVersion
  + AddXamlPage(path), RemoveXamlPage(path). CompilePass1/CompilePass2 add any .xaml file they are given that the build
    didn't know (a new page).
  * GeneratedText values are exactly the file on disk (they now end with the final "\r\n").
  * Hot reload builds (EnableXamlHotReload, the Debug default) generate shaped code: C# pass 1 file is <Page>.i.g.cs
    (not .g.i.cs), tombstones, MetadataUpdateHandler on XamlTypeInfoProvider, InitializeComponent re-init. The service
    takes EnableXamlHotReload from input.json, so it matches the build. Hosts: don't hardcode ".g.i.cs".
  * Hot reload state (connection ID ledger, member inventories) lives in the build's output folder
    (obj\...\XamlHotReload), whatever outputPath is. Run the service with outputPath = null.
  Host duties after a delta: run MetadataUpdateHandler types (ClearCache/UpdateApplication); before ApplyUpdate, reset
  _contentLoaded and call the old Bindings.StopTracking(). Bindings.Update() after re-init is now generated.

v3 (references reload)
  + ReloadInputs(CompilerInputs newInputs): a new input.json from a build of the same project (package or project
    reference added, removed or updated). Unchanged referenced files stay loaded; files rebuilt or deleted on disk and
    references that are gone are unloaded with every cache that points at them; new ones load on the next compile.
    A framework or WinUI reference change (mscorlib, System.Runtime, WinRT.Runtime, Microsoft.Windows.SDK.NET,
    Microsoft.WinUI, Microsoft.UI*, Windows*) releases the whole type universe instead (FullReset; next compile cold).
    Pages: the new inputs' pages plus pages added since that they don't list yet.
  + RefreshReferences(): the same inputs; picks up referenced files rebuilt on disk (a class library rebuild).
  + XamlReloadResult: Added, Removed, Released (full paths), FullReset, Elapsed.
  * After a reload, the next CompilePass2(..., regenerateTypeInfo: false) reports XamlTypeInfoMayBeStale (new
    references can bring types and metadata providers).
  + --serve: {"Op":"reload","InputJson":"<new input.json>"} or {"Op":"reload"} (refresh). The response carries
    Success, ElapsedMs, Added, Removed, Released, FullReset; errors in Diagnostics.
  The host still needs a build (restore + reference resolution) to produce the new input.json; the service doesn't
  resolve packages.

v3, unchanged API (per-page type info cache)
  * Hot reload builds: CompilePass2([page], image, regenerateTypeInfo: true) is byte-identical to a full pass 2 and is
    now the recommended response to XamlTypeInfoMayBeStale (Gallery p50 ~0.4 s; was ~0.8 s idle, 1.9 s loaded).
    The other pages' type information is replayed from the service's per-page cache.
    XAML_COMPILER_SERVICE_NO_TYPEINFO_CACHE=1 turns the cache off.

v4 (reload with pass 1 inputs)
  * ReloadInputs/RefreshReferences: when the new inputs have no LocalAssembly (pass 1 inputs: MarkupCompilePass1 writes
    IsPass1=true, CompileMode=DesignTimeBuild and no LocalAssembly to the same obj\...\input.json), the previous
    LocalAssembly and SdkXamlPages are kept. Before, pass 2 then had no project assembly and ignored the host's image
    (WMC0001 Unknown type for types that exist only in the image).
  + XamlReloadResult.KeptLocalAssembly; --serve reload responses carry "KeptLocalAssembly".
  * A service created from pass 1 inputs: CompilePass2 with an image now works (the image stands in for
    <OutputPath>intermediatexaml\<TargetName>.dll).

v4, behavior (no API change)
  * Builds with hot reload state record their code generation settings in <OutputPath>XamlHotReload\codegen.json
    ({"enableXamlHotReload":true|false}). A service compile (either pass) whose inputs differ fails with WMC9998 at that
    file instead of generating code the running build doesn't have. Typical cause: the host's input.json was written
    without EnableXamlHotReload (pass EnableXamlHotReload="$(EnableXamlHotReload)" to InputSerializer).

v4, behavior (no API change): short state file names
  * Files in <OutputPath>XamlHotReload are named by a 12-hex hash of the class name: <hash>.connids.json (ledger),
    <hash>.hotreload.json (manifest), <hash><ext>.members.json (for example <hash>.i.g.cs.members.json). They were
    <Class>.<hash>.xaml.connids.json etc.; a build deletes the old ledgers and manifests. Atomic writes go through ~<n>.tmp in the same
    folder (was <file>.<pid>.<guid>.tmp, which passed MAX_PATH in deep projects: WMC9999 "Could not find a part of the
    path"). When the folder itself is deep, it is addressed as \\?\<path>, so XamlCompiler.exe (.NET Framework) writes
    beyond 260 characters. If a state path still can't be used, the error is WMC9998 naming the path, its length and
    the limit, not an internal error. A build's state from an earlier compiler isn't read: rebuild after upgrading.

v4, additive: type information check
  + XamlCompilerService.VerifyTypeInfo (static; default: environment variable XAML_COMPILER_SERVICE_VERIFY_TYPEINFO=1,
    which --serve honors too). For hosts' test runs: a pass 2 that regenerates XamlTypeInfo and replays other pages'
    type information from the per-page cache also collects every page again without the cache. If the two
    XamlTypeInfo files differ, the compile fails with WMC9998 (first differing line in the message) and returns the
    full collection's XamlTypeInfo. Markers: "type info check" (identical/different, ms). About doubles that compile.

Host duty (no API change), Roslyn issues 3 and 5 in the design note
  * GeneratedText can hold files with no code: a ResourceDictionary without x:Class gets " \r\n" .g.cs/.i.g.cs (as in a
    build). Adding such a file to the workspace, like a generated file that changed only in '#pragma checksum', is a
    no-change update that Roslyn commits without a new baseline; the next update of a method added during the session
    then throws NullReferenceException (GetPreviousMethodHandle or GetDeletedSynthesizedMethods). Hold both back and
    hand them over with the next real change.

v4, behavior (no API change): stable XamlTypeInfo layout (hot reload builds, C#)
  * <OutputPath>XamlHotReload\typeinfo.json records the type table order of the last XamlTypeInfo (builds and service
    compiles); types keep their index and new types are appended, so adding a type mid-session no longer renumbers the
    table. Clean deletes it. Each user type's IXamlType is built in Create_<key>_<Name>; InitTypeTables and
    CreateXamlType dispatch to blocks of 64 indices. Normal builds (EnableXamlHotReload off) are unchanged.
